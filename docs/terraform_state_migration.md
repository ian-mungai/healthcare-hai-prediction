# Terraform state migration

Each stack kept its Terraform state in a local `terraform.tfstate` file. The migration copies each file once into the project bucket, checks the copy, switches the stack to the S3 backend and refuses a second run. The OIDC plan role stays off until all six stacks are moved and the owner turns it on in its own change.

## Design

- **Where:** the project bucket, key `terraform_state/<stack>/terraform.tfstate`, for the stacks `storage` (the `infra` root), `iam`, `platform`, `services`, `jobs` and `alerts`. Workspaces would use `terraform_state/<stack>/workspaces/`, so every state request stays under the prefix that the bucket policy and the plan role policy name.
- **Backend:** `infra/<stack>/backend.tf` holds the key, `use_lockfile = true` and `encrypt = true`. The lock is the S3 lock file `terraform.tfstate.tflock` beside the state (a conditional write), so there is no DynamoDB table. The bucket, the region and the profile come from `terraform init -backend-config` options, so no account value is committed. The migration script writes the file (`state_migration backend`) and the owner commits it after the move.
- **Protection** (`infra/main.tf`, switch `terraform_state_enabled`, applied by `owner/state_prefix_apply.sh`): versioning is on. Replaced state versions expire after 90 days and the current state never expires. The project user may read and write the state keys and the lock keys of the storage, platform, services, jobs and alerts stacks only. Every other principal is denied the whole prefix except the plan role and the administrator named in `terraform_state_admin_principals`. The project user and the plan role are denied `terraform_state/iam/`.
- **Approved inputs of the storage stack:** the switch and the administrator are inputs of the storage stack. A storage plan made without them removes the bucket's state statements and lifecycle rules. The wrapper therefore keeps the approved administrator in `plans/state_migration/state_protection.json` (owner only, written by `terraform.sh --state-admin ... apply` through `scripts/infrastructure/state_protection.py`). The record holds the administrator, a digest of the bucket and the account from `.env` (a record of another deployment is refused) and a status. The apply keeps it as `pending` before it runs. It becomes `verified` only after the apply exited 0 and the live bucket read back with the same detailed checks as the final check of the sheets (each state statement by its effect, principal, actions, resources and condition, the administrator in the prefix deny, the replaced-versions rule exactly as `infra/main.tf` writes it and no other rule that expires state). A pending record is no approval, so a failed apply leaves nothing approved. From then on the wrapper passes the verified administrator to the renderer on every storage render, so every plan and apply through the wrapper carries `terraform_state_enabled` and the administrator with no option. A different `--state-admin` is refused. The plan check at apply refuses a saved plan without them. `state_migration plan` for the storage stack stops without a verified record and stops again when the plan's variables do not hold the approved inputs.
- **A checkout without the record fails closed:** every storage `plan` and `apply` through the wrapper (not `validate`) reads the live bucket policy when it has no verified administrator. When the bucket already holds any state statement, the wrapper refuses the render, because a plan without the inputs would remove the protection. A policy that cannot be read refuses too. A bucket with no policy has no protection to remove. To remove the protection on purpose, run the plan and the apply with `--disable-state-protection` as their own owner step (it cannot be combined with `--state-admin`), then remove the record by hand.
- **Profile split:** the iam root is applied with the administrator profile, so its state is moved with `--admin-profile` and no other profile touches `terraform_state/iam/`. The other five stacks use the project profile of `.env`. The script refuses an administrator profile for a project stack and refuses the iam stack without one. It also refuses an administrator profile that signs in as the project user.

## What the script proves

`scripts/infrastructure/state_migration.py` first reads the bucket. The identity must be the project user (the administrator for the iam stack). The version history must be on. Each state statement of the bucket policy must be the one of `infra/main.tf`: the effect, the principal, the actions, the resources and the principal list of the condition for the two denies. The stack's own principal must be excepted from the prefix deny. The project user must be named in the iam deny. A state Sid that appears twice is refused. An unconditional deny that reaches the stack's key is refused. The lifecycle rule of replaced state versions must be enabled, cover `terraform_state/`, expire replaced versions after 90 days and not expire the current state. No other enabled rule may be able to expire the current state or lock object of any of the six stacks: each rule with an expiration in days or by date is checked against the twelve keys (`terraform_state/<stack>/terraform.tfstate` and its `.tflock`) by its prefix. A rule with only a tag condition, an object-size condition or a tag beside a prefix that a key has counts as reaching them. Only the default workspace moves. A named local workspace is refused before anything is copied. A selection other than `default` is refused too.

It then copies the state with a write that refuses an existing key, reads it back and compares the bytes and the fingerprint (serial, lineage, resource count and instance count). It runs `terraform init -reconfigure` (Terraform sees equal states, moves nothing and empties the local file) and reads the state through the backend with `terraform state pull`. The fingerprint must equal the local one at each step. The plan before and the plan after must give the same change list, which holds every resource change and every output change. A plan that exits with changes but lists none is refused. `verify` needs the exact recorded fingerprint (a newer serial is refused) and an S3 object whose SHA-256 equals the record, so it runs before any apply. The run is recorded in `plans/state_migration/<stack>.json`: stage `copied` before the switch, then `switched` once the state read through the backend equals the local one, then `done` only after `verify` passed. A stack with the record `done` is refused a second run. A remote key that holds other bytes than the local state is refused. A remote key with the same bytes is adopted.

A stopped run resumes from its recorded stage. After the copy and the backend file, `plan --phase before` keeps the list from before the move (a new plan cannot run on a stack with an uninitialized backend) and `migrate` continues. After the switch and before the last record, the sheet's first step (`check`) prints `check: resume`. The local state is empty by design, so that step checks only the identity. Then `plan --phase before` keeps its list. It stops when that saved list is missing, because a new list made through the switched backend would hide a change made after the switch: restore the original list from `plans/state_migration/` first. `migrate` reads the state through the backend and the bucket. When both equal the record, it writes `switched` and copies nothing. The sheet then runs `plan --phase after` and `verify`. Only `verify` writes `done`. A stop between `migrate` and `verify` (record `switched`) resumes the same way, in both move sheets. A failed read through the backend puts back the original local bytes and the backend settings Terraform cached before the switch (`.terraform/terraform.tfstate`). It prints `backend: restored` only after an ordinary local `terraform state pull` read the original state. When that read fails, the step ends with exit code 3 and the message that the stack is not back on its local state. The sheet then stops with the rollback pointer and no success line.

The E2E is `scripts/infrastructure/run_state_migration_e2e.py` (real Terraform and a loopback stand-in of the bucket). It covers the full run of all six stacks, the second-run refusal, an interrupted copy, a read-back mismatch, a lost write race, the refused starting states (including each policy and lifecycle defect and the named workspaces), the three resume points, a tampered verification, an output-only plan, the approved storage inputs, the shape check of the prefix plan (moves, imports, output changes and the delta inside the two resources), the fail-closed state protection, the lifecycle rules by key, the first prefix apply with no record, the retry against a live bucket with a wrong deny or a state rule that expires current state, the missing saved before-list after the switch, the failed restore, the profile split, a linked state file and the backend text.

## Owner order

1. `scripts/infrastructure/owner/state_prefix_apply.sh` (project profile): plans the state protection for the storage stack (no color codes in the log), reads the saved plan's JSON and stops unless it holds exactly two changes, both in place (`aws_s3_bucket_lifecycle_configuration.data` and `aws_s3_bucket_policy.tls`, each with the actions `["update"]`). It stops on a moved or imported resource or an output change. Inside the two resources only the state statements of the bucket policy and the two state rules of the lifecycle configuration may differ from the state. It prints the SHA-256 of the saved plan file. The question asks you to type `apply` and the first 12 characters of that SHA-256. The apply runs only if the file still has the same SHA-256. Then it applies that file and reads the live bucket. After a partial apply the record is still `pending`: run the sheet again. For an update that the new plan holds as no change, the shape check reads the live bucket and accepts the omission only when the live bucket shows that update (the detailed policy and lifecycle checks of the final check, with the administrator in the prefix deny). It checks and confirms the remaining change by its SHA-256 as before. When no change remains and both updates are live (the apply finished and only its read-back failed), the saved plan holds no change: you confirm it by its SHA-256 as usual, the apply changes nothing and the wrapper's read-back marks the record `verified`. A plan that holds both updates (the first apply) needs no record. Without a pending record of that administrator, a plan that lacks an update is refused.
2. `scripts/infrastructure/owner/state_migration.sh <stack>` for `storage`, `alerts`, `jobs`, `platform` and `services` (project profile).
3. `scripts/infrastructure/owner/state_migration_iam.sh` (administrator profile).
4. Commit the six `backend.tf` files. The OIDC plan role stays off.

## After the move

Terraform empties the local `terraform.tfstate` and keeps the old content in `terraform.tfstate.backup`. When the file is a link, Terraform empties the file the link points to. The script's own copy of the state stays in `plans/state_migration/<stack>.local_state.json` (owner only). Two project tools read a stack's state through Terraform (`terraform state pull`), so they work for a moved stack. `host_session` takes the serial of the services state from it. `alert_email` (`state_addresses`) takes the resources of the alerts state from it. An empty or missing local file counts as no state when the backend holds none. A state in the bucket counts when no local file exists.

## Rollback

Run every command below from the stack folder (`infra`, `infra/<stack>`) and write the record paths as absolute paths. Set `RECORD=` to the absolute path of the repository root's `plans/state_migration` folder first, because a relative `plans/...` path resolves inside the stack folder.

- **Stopped before `backend: switched`:** nothing to undo. The local state and the stack folder are as they were. A copy that was written stays in the bucket and the next run adopts it. If it holds other bytes, an administrator deletes `terraform_state/<stack>/terraform.tfstate` and the next run copies again.
- **A failed switch:** the script removes `backend.tf`, writes the original bytes back to the local file, puts back the backend settings that Terraform cached and checks that a local `terraform state pull` reads the original state. It prints `backend: restored` only after that check. Any other line starting `backend: restore failed` means the stack is not recovered. Copy `$RECORD/<stack>.local_state.json` to `terraform.tfstate`, remove `.terraform/terraform.tfstate` and `backend.tf` and run `terraform init -reconfigure -input=false -lockfile=readonly`.
- **After `migration: done`:** no apply may run. Then, in the stack folder:
  1. `terraform state pull > "$RECORD/<stack>.pulled.json"` (this holds any change applied after the move). Check that the command succeeded and that the file is not empty and is JSON (`python3 -c 'import json,sys; json.load(open(sys.argv[1]))' "$RECORD/<stack>.pulled.json"`). Stop here if any of them fails: the local state is still the old copy.
  2. Only then remove `backend.tf`, copy the pulled file to `terraform.tfstate`, remove `.terraform/terraform.tfstate`, run `terraform init -reconfigure -input=false -lockfile=readonly` and a plan through `scripts/infrastructure/terraform.sh`, which must show the change list of the plan after.
  3. Delete `$RECORD/<stack>.json`. An administrator then deletes the remote key before a new migration, because the remote state differs from the old local copy once an apply has run.
- **A stuck lock:** the lock file is `terraform_state/<stack>/terraform.tfstate.tflock`. Its content names the holder (`Who`, `Operation`, `Created`, `Info`). Read it with `aws s3 cp s3://<bucket>/terraform_state/<stack>/terraform.tfstate.tflock - --profile <the stack's profile>`. Unlock only when the `Created` time is old and the `Who` machine shows no Terraform process that works on that stack. A plan started inside the stack folder has no stack name in its command line, so check both the working directory and the command line of every Terraform process on that machine: `pgrep -x terraform` lists the process IDs, then for each ID `lsof -a -p <pid> -d cwd -Fn` shows its working directory and `ps -o command= -p <pid>` its command line. Any process whose working directory is the stack folder or whose command line has `-chdir=` with it holds the lock. A live holder is waited for, never unlocked. Then run `terraform force-unlock <lock ID>` in the stack folder with the ID from the lock content or the error. Terraform compares the ID with the lock and refuses a different one. Do not delete the lock key by hand, because that skips the ID check.
- **A lost local state:** S3 versioning keeps replaced versions for 90 days. The migration backup holds the pre-move state.

## Accepted risks

The threat model of the project (owner decision of Nov 20, 2026) is a trusted host. Inputs that a party with the project's own roles crafts are Info and are not defended against here:

- A wildcard role in the deny exception list of the bucket policy. The policy check compares the principals it requires and refuses an unconditional deny that reaches a stack's key, but it does not judge extra principals in the exception list.
- `TF_WORKSPACE` or `TF_DATA_DIR` set in the environment of the owner's shell. The script refuses `TF_CLI_ARGS*` and the named local workspaces it finds in the stack folder, but a variable that moves the workspace or the data folder of Terraform changes what `terraform state pull` reads.
- A hand-swapped pulled state, which is a state source replaced by hand between the steps. The fingerprint (serial, lineage and counts) and the digest in the record catch a change by accident, not one made on purpose by someone who also edits the record.
