# Restore after a teardown

After a teardown or the loss of the host data volume, `host_session start` brings back the state that matters without hand steps once the owner steps below are done. Creating the data volume from a snapshot stays a documented manual step. Airflow logs and Grafana edits are not restored.

## What is kept

- **Postgres:** each database that holds tables (`polaris`, `airflow`, `mlflow`, `mlflow_auth` and `openmetadata_db` where they exist) is dumped with `pg_dump -Fc` and uploaded to `pg_backups/<database>/<UTC>.dump` in the data bucket.
- **Completion marker:** after every dump of a set is uploaded, `pg_backups/complete/<UTC>.json` lists each dump with its size, SHA-256 and table count and records the databases of the set (`members`). A dump without a marker is never restored.
- **Write once:** every key is created with `If-None-Match: *` under a role that can only create objects under `pg_backups/`. Nothing is replaced and nothing is deleted by the project. A bucket rule expires the prefix after 30 days.
- **Catalog snapshots:** each publish writes `catalog_backup_<run>.json` before it commits, so it is not a recovery source. The commit step also writes `catalog_committed_<run>.json` under the same folder after `main` of every table is at the committed snapshot and the run row exists. The snapshot is created once with a conditional write, a rerun leaves one whose JSON content is the run's state and refuses any other. The ledger entry of such a snapshot may hold other runs' rows but must hold this run's own row with the same snapshot set. The layer driver checks it before the upload. A run published before this change has no snapshot and is not recovered.
- **Code run record:** `host_session` writes the run ID and digest of the code it placed to the object `lakehouse/host_state/code_run_record.json` in the data bucket, which the project user can already write. The record is a plain text line.

## How the backup runs

The `postgres_backup` service runs two containers on the host. The dump container waits 15 minutes after it starts and then dumps every six hours. A run is refused and nothing is uploaded when a dump does not read back completely, lists no table or passes its 15 minute deadline. An empty database refuses the run. The upload container checks every dump again, uploads the set and writes the marker last. The last result of each step is in `last_result.json` and `upload_result.json` in the backup folder of the host for the monitoring push that merges separately.

## Final dump at stop

The interval dumps leave a gap: whatever the databases gained after the last dump is lost at the next start. The restore never sees it. `host_session stop` closes the gap. After the job task check and before the catalog drain and the host-off request it scales the `postgres_backup` service to zero, waits until its task has stopped and runs the `postgres_final_backup` one-shot. That task runs the same dump and upload scripts as the service, one pass each (`PG_BACKUP_ONCE=1`, no first delay). The upload container starts only when the dump container exited 0. The marker is written last. A final set that stopped half way has no marker, so the restore never selects it. The final set is the newest marker, so the next start restores from it.

- A failed or late final dump never holds the host on. `stop` reports `final_backup_failed` with the task name and the exit codes of its containers and turns the host off anyway. The newest usable completed set stays the restore point. A failed stop would leave a billed host running with nobody present. The wait for the one-shot ends after 1800 seconds and the wait for the service to stop after 300 seconds.
- An interrupt or SIGTERM during the final dump is reported as `final_backup_interrupted`. The catalog drain still runs. The verified host-off follows. The interrupt then propagates.
- A host-off request that the provider refuses with an error code (for example an Auto Scaling `AccessDeniedException`) leaves the host on. A timeout, a CLI read error or an unreadable answer is no refusal: the request may have been applied, so nothing is given back and the host is not reported as staying on. After a refusal, when the final task is known to have ended or never to have been launched (also after a refusal of the final `RunTask` while ECS lists no final task), `stop` sets the `postgres_backup` service back to the count it had before the scale-down (saved before the write, so a lost reply does not lose it) and reports `backup_service_restored`. The refusal is the error `stop` raises. When that call fails it reports `backup_service_restore_failed` and the refusal stays the error. While the final task may still run, the service stays at zero, so two dump containers never share the backup folder.
- A dump script that cannot be read in the checkout is a failed final dump, reported by name. The cleanup of a failed `start` then still turns the host off. The start error stays the one `start` raises.
- The dump is skipped and reported as `final_backup_skipped` when the stack plans no `postgres_final_backup` task (the backup is off or the services apply of this change is not done yet) and when the postgres setup of the running task is not complete, because a dump of databases that did not get their restore would hide the older sets.
- The cleanup of a failed `start` takes the same dump, within 900 seconds, only when the services had become stable and never with `--keep-on`.
- The next `start` sets the backup service back to one task.
- **Checked revision and task binding:** before it touches the backup service, `stop` reads the registered `postgres_final_backup` task definition and compares the dump and upload scripts in it with the files of the checkout. A definition that was applied before a change of the scripts reports `final_backup_failed` ("apply the services stack") and takes no dump. The host still stops. The launch names that revision, not the family name, so ECS cannot start a newer one that was not checked. The launch also gives both containers a new task ID (`PG_BACKUP_TASK_ID`). The dump step writes it into `last_result.json`, which it publishes whole under a temporary name and renames. The upload step takes only the set that this result file names. It refuses a result file of another task. A task that stops without an exit code for both containers is not reported as taken.

### Known limits of the final dump

These are recorded limits, not open defects. The operating rule is **one host sheet at a time**: one `host_session` command runs against the host at a time. No job is launched while it stops. The final dump holds no launch lock and takes no lease, so these cases are not covered. They wait for the end of the project with the other hardening.

- Two host stops that overlap. Also a forced stop (`--force-stop`) while another holder has the services apply lock.
- A host job that still runs and is not yet visible to ECS when the host stops. The stop then ends it with the host. Its launch stays unresolved until the settle records it as cancelled.
- Two final dump containers that race on the shared backup path. Each dump writes its set under a name made from the second. Both containers share one result file. A dump that finds a set of its own second still in the folder (an earlier pass that the upload has not taken) is refused and exits 1, so it never nests inside that set.
- A refused final launch retry that resumes the interval backup beside a final task that is still running. The first launch is applied and its reply is lost. The retry with the same token is then refused by the provider, the host-off request is refused too and ECS does not list the task yet. The interval service gets its count back. What still protects the project: the dump step refuses a run key whose set still exists. The upload step takes only the set of its own task. The restore reads only sets that have a marker, which is written last.
- A marker whose `members` field is null. The restore reads it like a marker written before the field existed and skips the membership check. What still protects the project: only the project's uploader writes markers and it never writes null. The backup role may create each key once. It may not read or replace it. Every entry of the marker still has to match its size and SHA-256.
- A complete interval set that still waits for upload when a database is enabled. The upload step compares it with the new database list, refuses it and sets it aside as `<run>.refused`, so nothing of it is uploaded. What still protects the project: the published sets stay usable. The next interval dump covers the new list. The final dump at the next stop does too. The refused set stays on the volume until its keep time ends.
- A lock release whose read-back is malformed. The release is reported with the lock name and left in place.
- A final task that ECS acknowledged and then reports as `MISSING` for a while. The stop reports the dump as failed and turns the host off. The newest usable completed set stays the restore point.

## How start restores

1. `host_prepare`, then the code checkout. Without `--code-run`, a host that has no checkout or no record reads the code run record from the data bucket and installs that archive.
2. The postgres task starts. `postgres_restore_fetch` reads the newest marker that is well formed (schema 1, its own run, every entry checked, every database that its own `members` list names present) and whose every requested dump that the set holds matches its size and SHA-256. A set that was whole when it was written stays usable after a database is enabled later: the new database has no dump in it and the databases step creates it empty. A marker that records no `members` (written before the field existed) is read as before: it must hold at least one requested database, each one it holds is restored and the databases step creates the others empty. A marker that lacks a database it lists is skipped. It streams each dump to disk in 1 MiB chunks. It falls back to an older set when the newest is malformed or damaged.
3. `postgres_databases` creates the roles. A database that has data is never touched. A missing database that has a dump is restored in one transaction into `<database>__restore`, checked against the table list of the dump and renamed only after every database passed. `polaris` exists empty from the image, so it is restored in place in one transaction. A missing database with no dump is created empty, as before.
4. `host_session start` does not call the services stable until the fetch container and the databases container of the current deployment have both ended with exit code 0. A pending or running container is not completion. A task of an older task definition is not completion either. A failed fetch or restore makes `start` stop with the named reason and turn the host off. No database was made visible, so no service starts on half-restored data.
5. After the services are stable, the `mlflow_user` task creates or checks the model API user and its READ grants. It refuses a stored password that the existing user does not accept. It refuses a DENY grant, on a model, on an experiment and on an experiment in the trash. It ends at its run deadline even when a closing response stalls. It never reports the account ready after a refusal. When the model API login is not stored yet, the task checks nothing and exits with code 3. The host session then reports `mlflow_user_skipped` instead of ready. The start goes on. The serving secrets tool runs the same check, from `infra/services/scripts/mlflow_user.py`, after it creates the secrets. The OpenMetadata bootstrap starts one search reindex when the catalog has tables and the index is empty.
6. `start` launches the catalog restore before the online store reload in three cases. The databases container logged a restore. An earlier start left the pending marker `lakehouse/host_state/catalog_recovery_pending.json`. The log or the marker cannot be read. The restore is the `restore` step of `aws_catalog_setup`, the catalog setup one-shot, which runs on the host under its own role with the root credential. It reads the newest post-commit snapshot `catalog_committed_<run>.json` of the gold, silver and features folders from the data bucket, never the pre-commit `catalog_backup_<run>.json`. It registers absent tables. It advances tables whose catalog file is older. It checks that every table resolves to the committed snapshot. The marker is written before the run and removed only after it succeeds, so a failed recovery is retried by the next start. When the marker cannot be written, `start` fails without running the recovery and keeps the obligation as the file `data/host_session/catalog_recovery.pending` on the Mac, which the next start finds. If even that file cannot be written, the message says to run the restore by hand. A failure fails `start`. A folder with no snapshot contributes nothing. You can also run it by hand: `python -m scripts.infrastructure.host_session catalog-setup restore --dry-run` once the host is on and the services are stable, then without `--dry-run`.

## Turn it on (owner order)

1. Infra root: apply the lifecycle rule `expire_postgres_backups`.
2. IAM: set `restore_after_teardown_prepared` and `host_catalog_setup_prepared` and apply. The catalog setup role then also reads the three catalog backup folders. Apply the project user policy that adds the three roles to its pass list.
3. Lower `host_job_cap_mib` to 22528 or less in the same services apply: the new containers reserve 192 MiB more.
4. Services: set `postgres_backup_enabled`, `postgres_restore_enabled`, the three role ARNs from the IAM output `restore_after_teardown_roles`, `postgres_backup_bucket_name` and `catalog_setup_task_role_arn` from the IAM output `host_catalog_setup_role`, then apply. Without the catalog setup one-shot a start that restored a database cannot restore the catalog and says so. The same apply registers the one-shot task definition `postgres_final_backup` for the final dump at stop. It needs no IAM change: the project user may already run tasks of the project's families and pass the backup role.
5. Start the host and wait for the first backup (15 minutes plus the dump time). Check `pg_backups/complete/` for a marker.

## Drill (first live proof)

1. Wait for one marker. 2. Stop the host. 3. Move the postgres data folder aside on a scratch host or delete the data volume in a test project, never the live one without approval. 4. `host_session start` and read `restored database` lines in the postgres log. 5. Read the `catalog_restored` line of the start or run `catalog-setup restore --dry-run`, then compare the counts of tables in Polaris with the last catalog backup.

## Proof against a real server

`python -m scripts.infrastructure.run_postgres_backup_e2e` runs every script against stand-ins and is part of the configuration checks. `python -m scripts.infrastructure.run_postgres_restore_real_e2e` runs the same scripts against a scratch PostgreSQL 17 server and real client programs, dumps it, wipes it, restores it and compares a hash of every table. It is a heavy run: read its docstring for the environment it needs. It refuses a server that holds any of the project databases.

## Limits

- Backups expire after 30 days. A project idle for more than 30 days has none left.
- A dump is written every six hours while the host is on, so a restore returns the state of the last completed set.
- The MLflow and OpenMetadata routes in the new steps are unproven against the live servers.
- The catalog restore step is proven against a stand-in Polaris and stand-in snapshots and by policy evaluation of the task role. It is unproven against the live Polaris and the live data bucket.
- The newest snapshot of a folder is the one that S3 stored last, because a run ID holds no time. Under the task role the step reads the three backup folders only. It writes nothing to S3.
