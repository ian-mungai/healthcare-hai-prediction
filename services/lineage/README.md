# Local lineage services

The launcher owns PostgreSQL, the Marquez API and the web UI. PostgreSQL joins only the internal backend network and has no published port. The API is created on the frontend network and the launcher joins it to the backend network before it starts, because the Docker API version the launcher speaks (v1.43) creates a container on one network only. The UI joins only the frontend. API and UI host bindings must use `127.0.0.1`. [Lineage service guards](../../orchestration/lineage_services.py) validate closed settings and final container port bindings after interpolation. Data transformation jobs join neither lineage network. The host emitter delivers events.

The launcher computes service memory limits, generates private runtime configuration, waits for health and records creation and removal of both networks. Teardown confirms that the registry owns no remaining lineage container or network before releasing its service limits. Configuration and database state belong under ignored runtime storage.

## Declared dataset and model records

Every broker launcher row requires `lineage` version 1 with `inputs` and `outputs`. A dataset contains `namespace` and `name`. Requests carry caller identity, without dataset metadata.

For dbt model lineage, the launcher row also supplies `dbt_nodes`: fixed native dbt resource IDs mapped to dataset identities already declared by that row. The broker freezes these bindings in the intent. Each executed model output must be a declared output. Each dependency must be a declared input or an internal declared output. An unknown binding or dataset fails closed with the executed model named. Ephemeral dependencies are traversed without inventing a physical dataset.

The launcher injects `DBT_ENV_CUSTOM_ENV_HAI_ATTEMPT_ID` into a captured dbt attempt, together with `DBT_PARTIAL_PARSE=false`. Both native artifacts must carry the same invocation and that attempt ID. The silver and gold jobs of one run share a `target` folder. dbt's partial parsing keeps the environment recorded in a saved manifest. Without the full parse the second attempt's manifest would name the first attempt, so its capture would be refused. dbt documents this metadata mechanism in its [artifact reference](https://docs.getdbt.com/reference/artifacts/dbt-artifacts). The launcher freezes the bytes of `manifest.json` and `run_results.json` in private attempt storage and records their SHA-256 values. A repeated collection reuses the completed capture. The broker parses only bytes matching those recorded hashes. When the launcher recorded a capture failure for an attempt, the broker closes the submission `failed_closed`. It keeps the launcher's known capture message as written. Any other recorded text becomes a fixed message, so no recorded text reaches the ledger. A capture record that is present but malformed keeps the closed-contract text.

The closed `data_contracts/orchestration/dbt_lineage_record.schema.json` contract persists accepted model edges, invocation identity and artifact hashes. The host emitter reads that record and emits model runs with a parent task run. It reads no artifact path, SQL or environment metadata. Fixture rows retain physical DuckDB file identities. Separate model runs do not imply that those files became independently published tables.

The output snapshot contract is `data_contracts/orchestration/snapshot_record.schema.json`. A trusted producer supplies immutable output IDs bound to the full broker invocation. Missing snapshots remain flagged and are never fabricated. Row authors must declare a dataset before binding either a model or an output snapshot to it.

## Pinned input snapshots

The input snapshot contract is `data_contracts/orchestration/input_snapshot_record.schema.json`, version 1. It has the shape of the output record with `inputs` in place of `outputs` and the same closed identity kinds: a SHA-256 for a file, a signed 64-bit snapshot ID for an Iceberg table and an object version for S3. A fixture run may name only local files. The output record stays at version 1 and is unchanged.

The broker builds the record. It never accepts one from a job. It validates the record against the full invocation, the inputs the row declared and the pins frozen in the intent line. It refuses an undeclared input, a repeated input, a declared input without a pin, another invocation, a malformed identity, a value that differs from its pin, a known secret and any run that failed or was cancelled. A refused record fails the submission closed and persists nothing. The host emitter validates the record again and adds the OpenLineage `version` facet to each declared input of the START and terminal events. A run without a record keeps its inputs without a facet and nothing is fabricated.

In fixture mode the broker pins each declared file input before it sends anything to the launcher. A declared name `data/analytics/dbt/runs/<run_id>/<path>` stands for `<path>` in the broker's own run folder, `runs_root/<run_id>`, wherever the checkout is. The pin and the facet keep the logical name. The broker opens the run root, then every directory below it through its parent descriptor without following a link, then the regular file the same way. The broker hashes the bytes and writes the result to the intent line as `input_pins`. A new fixture submission whose declared inputs cannot all be pinned is refused before anything is appended or forwarded, with a reason that names no path: an input that is not a local file, a name outside that prefix, another run's name or a source that is absent, linked, not a regular file or over 512 MiB. Recovery of an intent written without pins is unchanged and such a run emits no input facets. Other modes and rows without inputs have no pins. A retry returns the first intent, so a job that edits its input cannot change its pin. A pin is the bytes at intent, not proof that the job read them.

For real and publish fixture runs the pin step supplies the trusted source, never the consuming container. The pin step writes `data/analytics/dbt/runs/<run_id>/pins.json` once, a flat object of bronze table to the snapshot ID of its `main` branch. The launcher records the SHA-256 of that file only when it equals the digest the writer printed and reports it as `pins_sha256` with `pins_unchanged` through `status what=run`. A real run builds its input record from that file after the broker confirms that its SHA-256 equals the launcher's recorded digest and maps each table to the declared dataset `bronze.<table>` in its Iceberg namespace with kind `iceberg_snapshot`. L2 builds none of this. The first real publish carries the requirement. Its verification must show the pinned IDs on the input datasets in Marquez, compared with `pins.json`.

## Provider transport and delivery

The pinned official Airflow image supplies the OpenLineage provider. `openlineage.yml` selects the local `provider_transport.SafeTransport`. The orchestration Compose file mounts this folder read-only as `hai_lineage` on the image's Python path and mounts a private writable provider spool into the scheduler and the API server only. The provider transport makes no HTTP or broker request. It keeps native DAG and task run UUIDs, exact caller fields, UTC time, state and the native DAG parent. Dataset lists are empty at this boundary. SQL, task source, environment, error text and arbitrary provider facets are discarded before persistence. An unmapped task may use a null or minus-one map index. Mapped tasks are refused because v2 carries no mapped-task identity.

The supervisor starts a separate bounded collector and joins it during teardown. `delivery.json` supplies the loopback API port, interval, pass deadline and batch limit. Test sessions collect without HTTP unless an explicit lineage API port is supplied. Collection matches `dag_id`, `task_id`, `dag_run_id` and `attempt` to the approved v2 broker caller. Host task events retain the provider's native task UUID and DAG parent. Model UUIDs derive from that task UUID. Declared identities shared between two DAGs remain identical. A missing match defers the durable completion record. A conflicting match fails closed.

The SQLite outbox keeps immutable event bytes and acknowledgments. Provider collection traverses chronological spool names. Pending delivery sorts by event time and lifecycle state. A failed request keeps the unacknowledged payload for resend with the same run and event identity. Collection and delivery run outside the broker's completion and ledger locks. Storage and validation failures report exception types and retry in the next pass. These mechanisms require the native scheduler and Marquez checks below before acceptance.

Raw provider envelopes remain sanitized and immutable in the outbox. Native task callbacks wait for two completed record traversals, so a completion written before the traversal cursor is revisited before its absence is inferred. Only the matching validated host task event can supply declared datasets and snapshot facets. Delivery of that task's queued events waits for this projection. Other task identities keep their own delivery state. A START or RUNNING callback that arrives after an acknowledged host terminal event is retained with a covered disposition and is not sent as a state regression. Native terminal callbacks retain their state and receive only trusted dataset metadata. SQLite progress handlers apply the pass deadline inside queries as well as between operations.

## Verification commands

These checks use renderers, synthetic native artifacts, the lineage database dump writer against a stand-in `psycopg2` and broker completion in-process. They start no launcher daemon:

```sh
.venv/bin/python -m scripts.orchestration.run_lineage_services_e2e
.venv/bin/python -m scripts.orchestration.run_lineage_amendment_e2e
.venv/bin/python -m scripts.orchestration.run_lineage_e2e
.venv/bin/python -m scripts.orchestration.run_lineage_completion_e2e
.venv/bin/python -m scripts.orchestration.run_contracts_e2e
```

These runners start disposable test launchers and require the project's exclusive heavy slot:

```sh
.venv/bin/python -m scripts.orchestration.run_lineage_provider_e2e
.venv/bin/python -m scripts.orchestration.run_lineage_stack_e2e
.venv/bin/python -m scripts.orchestration.run_lineage_launcher_e2e
.venv/bin/python -m scripts.orchestration.run_lineage_launcher_e2e --partial-parse
.venv/bin/python -m scripts.orchestration.run_lineage_launcher_e2e --real-artifacts
.venv/bin/python -m scripts.orchestration.run_lineage_scheduler_e2e --case graph
.venv/bin/python -m scripts.orchestration.run_lineage_scheduler_e2e --case outage
.venv/bin/python -m scripts.orchestration.run_lineage_scheduler_e2e --case failure
```

The provider runner inspects the pinned Airflow image without installing packages. The stack runner requires cached digest-pinned images, checks service health and host reachability and tears down its own stack. It does not pull a missing image. The launcher bounds each stack start at 600 seconds from admission. An expired limits, network or pre-start service phase ends in a named timeout and the owned teardown. The launcher records the timeout even while Docker is unavailable, reconnecting or restarting. Cleanup then waits for Docker and keeps the service limits and networks until absence is confirmed. A started service then answers to the launcher's health wait. The launcher lineage runner uses a fake engine and synthetic producer by default. Its rows are test-only `publish_fixture` rows that select the `fixture_dbt` template. They keep the shared Iceberg dataset between two DAGs and runs. They claim nothing about publish input provenance. Its `--partial-parse` mode runs two captured dbt attempts of one run on one shared `target` folder through the real launcher and broker with a fake engine whose script plays dbt, including its partial-parse manifest reuse. The second attempt must be captured. A stale manifest must close with the launcher's recorded capture failure. Any other recorded failure text must close with the fixed message. None of that text may reach the ledger, including secret-shaped values, paths and tokens. Its `--real-artifacts` mode runs one offline tiny fixture through a real test launcher to check native dbt metadata and capture. Those checks do not prove a real catalog publication or Marquez graph acceptance. Reports remain under ignored `data/e2e/` folders.

The scheduler runner prepares separate graph, outage and forced-failure cases on the existing tiny native dbt fixture. It runs in a private checkout. The finite `lineage_dump` template runs a read-only dump over the internal backend with the existing Airflow image. The privacy check requires a known native run UUID in that dump before scanning it, the provider spool and the outbox for planted values and the broker token. The runner retains private evidence and confirms cleanup through approved launcher outcomes and process metadata. It never opens registry files. Each case has a 420-second work deadline and a 120-second cleanup deadline. Its deliberate mutations check correlation, delivery and sentinel detection. A valid failing-first result must include completed setup, the reached subject, a mutation invocation, the intended named failure and clean teardown. A reviewed detached-launcher bytecode isolation solution is required before a shared host environment can be used for a heavy check.

Native provider correlation, split-network host reachability, native artifact capture, scheduler graph, real outage recovery, forced failure and database privacy require a heavy run. The graph case also checks, for every successful fixture invocation that declares inputs, that its intent pins equal its record and that its own host events, delivered outbox events and the raw rows Marquez stored carry those versions on START and the terminal event. An event belongs to an invocation only by job namespace, job name and native run UUID, resolved from the invocation's exact native caller link, so one invocation's events never satisfy another. Marquez must also show the pinned identity of the fixture input, equal to the digest of the bytes the fixture seed planted. The outage case counts the raw `lineage_events` rows in a database dump taken after recovery and requires exactly one row for each delivered event. A row matches an event when the whole event is equal once its time is written as a UTC instant with nine fraction digits, because Marquez stores the time as `Z` and the outbox holds `+00:00`. A dropped, doubled or altered event fails. A time that differs by one nanosecond also fails. It then forces a lost-reply resend and requires the Marquez runs and states to stay unchanged. It records the raw row counts after that resend without asserting them.

The stack runner probes this host's own addresses only. Its report names that scope as `host_coverage` and lists Verification 5 as pending. Reachability from a separate LAN device remains a separate acceptance check. `--hold-seconds <1 to 3600>` keeps a passing stack up for that long or until the `release` file appears in the run folder, so the owner can try its API and UI ports from a second device over IPv4 and IPv6. The addresses go to the ignored `hold.json` in the run folder and never to the terminal or the report. The launcher, provider Compose integration and Docker-call binding changes are implemented. Their native verification is pending. Output snapshot v1 provides declared output versions. Input facets come only from the closed input record above.
